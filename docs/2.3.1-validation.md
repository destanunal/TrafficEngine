# Traffic Engine 2.3.1 validation

## Railing paint

The supplied official shared-profile download (`https://api.curseforge.com/v1/shared-profile/pLVewiGa`) was read successfully. Its manifest identifies Create: Coaster Colony Client, Minecraft 1.21.1, NeoForge 21.1.255 and 189 mods. Sodium is 0.8.13+mc1.21.1, project 394468/file 8756580. The archive contains no replacement Traffic Engine model/texture assets.

Painted standard, gate and sloped railing models inherited thin-cap UV spans against a 1px white sprite. The exact downloaded Sodium 0.8.13 CompactChunkVertex.encodeTexture/sign bytecode reproduces coordinates escaping that sprite when small spans collapse during packed-UV quantization. This establishes a real texture-addressing failure; it is not a full modpack reproduction.

All 144 painted model aliases now share one dedicated opaque-white 32px sprite. The existing FaceBakery return hook moves only that sprite's UVs to its interior during resource/model baking. Other textures, face positions, normals, tint indices and light data are untouched. The shared inherited geometry remains shared. Painted hit/break particles use the same sprite. No new renderer, model wrapper, live block-entity lookup, per-frame/per-tick work, world scan or network packet was added. The 32px sprite leaves room for filtering even at mip 4; its RGBA mip chain through level 4 is 5456 bytes before driver overhead.

`checkRailingPaintUV` passes 38,913 assertions per Minecraft branch: 26,020 tinted faces, attribute preservation, production bake-hook wiring, the exact Sodium encoder, 1K..32K atlas dimensions and mips 0..4. Twenty old edge-escape cases reproduce in that matrix; the replacement coordinates remain inside white texels. The exact Sodium methods are isolated into a test class with ASM, without initializing or executing the downloaded mod. The game, full pack, server synchronization, graphics-driver output and FPS/RAM usage were not measured.

## Request button upper/lower pole (follow-up correction)

The lowered button's negative-Y centre stem overlapped the full-height sign post/footing below it. The previous upper cap also used a literal texture path in a face, which Minecraft resolves as a named slot and therefore produced the missing-texture sprite. Both failures are corrected.

Only housing/clamps are lowered now. A single normal-textured stem owns button-local Y=0..16 and its top face uses the valid `#metal` slot. A derived `lower_pole` state suppresses the negative-Y stem when the block below already owns it (vertical sign post, pole footing or another request button). Direct layered supports and railings retain their needed lower extension, shared across orientations and powered states through eight small multipart models. No housing model is duplicated. Internal shared caps are omitted; housing height, clickable region and the gapless upper connection are retained.

Placement and lower-neighbour events calculate the state with at most two support reads. Existing/copied button states are reconciled once on the existing server ticker after load; subsequent ticks add only a boolean guard and perform no new terrain reads, scans or allocations. Shapes use a fixed 9x4x2 table (72 entries), with no world query on shape access. Active/powered/waterlogged data is preserved during reconciliation and the press-release schedule is untouched.

`RequestButton231ModelCheck.py` passes 576 full assembly combinations per branch, including all heights, four facings, support ownership, water and active/powered states. It checks that button and lower carrier never draw the same stem region, that direct supports keep their connection, and that the housing stays lowered. The Java check also uses Minecraft's actual BlockModel material resolver on every base sunk face, catching the previous invalid cap reference; it validates shape agreement, cache identity and bounded/idempotent support changes. This remains headless verification; in-game visual/FPS testing has not been performed.

## Pole footing texture scale follow-up

The footing already referenced `trafficengine:block/sign`, but every metal face stretched the same UV rectangle [6,6,10,10] across the pole, neck and shoulder. The connected footing, all eight sunk models and the shared wrench support now use one source texel per model unit, matching the normal post texture scale. Face UVs remain within 0..16. Buried stems longer than 16 model units are split at Y=0 with no caps on that internal join, preserving their exact volume and avoiding out-of-atlas sampling. Inventory models inherit the same corrected footing asset. No Java/render/tick/network behavior is added.

Targeted asset inspection passed 190 metal faces and all nine footing stem volumes per branch, including texture slots, safe UV bounds, unchanged foundation UVs, internal-cap omission and item inheritance. Both branches' common compileJava checks passed. In-game visual comparison has not been performed.

## Blueprint capture

Painted and automatic road variants have no direct inventory item. Capture and material accounting now resolve these to their normal road or slope item; painted/automatic slopes resolve to slope material rather than full road blocks. Plain and painted slope layers are charged individually, so undo refunds match consumed layer items.

Selection edges allow 32 cells while total scanned volume remains capped at 4096. A 1x20 strip is accepted; a 32x32x32 selection is rejected. Capture and saved-plan decoding share that bound. Empty cells were already skipped and remain skipped. The 512 occupied-cell, 4096 repeated-cell, 192KiB plan-data and bounded undo-cache limits remain unchanged. Work remains user-triggered and placement uses the existing bounded queue.

## Curved pole join shading follow-up

The diffuse formula was continuous in angle but each longitudinal segment still used a single face normal. Adjacent underside segments differed by up to 0.053274 brightness, leaving visible bands. Model metadata now stores shared shade normals at longitudinal joins, preserving the square tube's hard side corners and the exact upright endpoint. Resource baking transforms these normals with the block facing and precomputes their coefficients. Vanilla and Forge/NeoForge output hooks apply per-vertex diffuse brightness while retaining existing world lightmaps, AO and RGB lighting. Geometry, face count, collision, quality settings and texture assets are unchanged. The loader reuses its existing four-value brightness buffer, with no new render pass, tick work or per-quad allocation during terrain rebuilds.

Asset checks compare 96 shared corners in four facings per branch: their calculated brightness differences are below 1e-7. Live in-game comparison and FPS measurements have not been performed. Optional renderer pipelines that bypass vanilla/loader quad output retain their previous lighting behavior.
