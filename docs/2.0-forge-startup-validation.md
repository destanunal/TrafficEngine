# Forge 1.20.1 startup fix validation

The development startup log failed before Minecraft initialization because Mixin 0.8.5 rejects injection annotations on the VertexConsumer interface. Public/default handler visibility alone does not make these injections supported.

## Change

- Removed EmissiveVertexConsumerMixin and its configuration entry.
- Reused the existing concrete ModelBlockRenderer and Forge QuadLighter hooks for emissive AO/light arrays.
- Added concrete item and block-preview render hooks. The item hook supports the vanilla and Forge alpha/read-color signatures; an injection group requires exactly one matching call.
- Shared brightness/light arrays are reused. No new world scans, ticks, render passes or emissive per-quad array allocations were added.

## Validation

- Passed :common:compileJava, :fabric:compileJava, :forge:compileJava and :common:processResources with the compile-only packaging guard.
- Passed a real Forge 47.2.1 / Mixin 0.8.5.12 bootstrap probe using compiled class directories, without producing a JAR or opening a world. VertexConsumer, ModelBlockRenderer, ItemRenderer and QuadLighter all transformed successfully; process exited 0 with STARTUP_PROBE_PASS.
- The source-only probe omits the Fabric-only tooltip mixin, mirroring the Forge Architectury transform that normally removes its @PlatformOnly(FABRIC) handler. It retains all production emissive hooks. Probe source and complete log are in the chat workspace, forge-startup-check.py and forge-startup-check/stdout.log.
- Passed 15 native regression assertions covering emissive item/preview brightness arrays, ordinary item rendering, Forge alpha/read-color preservation and world emissive light/AO.

This supersedes the earlier handler-visibility-only check: that check did not execute Mixin and therefore did not establish compatibility with interface injection restrictions. The probe validates startup transformation, not full modpack gameplay or the separately reported teleport freeze. No release/test JAR was created.
